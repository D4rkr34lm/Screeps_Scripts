## General Architecture

To make this bot easily extensible and fun to develop I split the runtime into three main parts:

- `Colony`: This is the main organizational unit of this bot. Every colony is responsible for a single origin room, as well as all the rooms it has claimed as remote. Additionally each colony manages, its resources, creeps, and tasks. To make it easier to handle early stages of a colony without building massive abstractions to make later colony stages work efficiently, the behavior of a colony - spawning, task generation, resource allocation, etc. - is defined via the `ColonyStage` of a colony.
- `Tasks`: This is a small parameterized unit of work executable by any creep who is declared to be capable of doing so via its `Role`. Tasks are generated by the `Colony` and are executed by the `Creep`. Their assignment is handled via the TaskAssignment-System in the `main-loop`.
- `Roles`: Roles are generally just a creep definition, to whether it can complete a certain task and how its body should be composed.

The bot generally uses a `declare&use` pattern, where behavior is defined in a declarative way, while the actual execution of behavior is handled by the main loop. This allows for a very flexible and extensible bot, where changes to behavior do not require a lot of changes to the core logic, keeping the potential for error and creating a bug in a unrelated part of the codebase low.

## Algorithms

This section contains breakdowns of the more complex algorithms and logic systems within this bot, who go beyond simple data transformation or conditional logic.

### Task Assignment

Version: `1`

The current system works on by collecting unassigned tasks and idle creeps, and then  matching them where possible using a `greedy` strategy. This means that the first task in the list of unassigned tasks is assigned to the first idle creep who is capable of doing it, and then both the task and the creep are removed from their respective lists, before moving on to the next task.
